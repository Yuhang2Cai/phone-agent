# 饭搭子 AI Android UI 重构规格

**Status:** ready-for-agent

## Problem Statement

当前 Android 页面仍然带有功能演示页特征：内容层级不清晰、首屏空白较多、核心入口分散、控件样式不统一，AI 助手与点餐主流程之间的关系不够明确。现有业务接口和后端闭环已经具备，但 UI 重构缺少统一的页面状态、导航、恢复和验收约定，直接开发容易造成页面之间行为不一致，或破坏已有的登录、搜索、购物车、订单和模拟支付流程。

## Solution

将 Android 客户端重构为轻盈、温暖、可信且高效的外卖首页与 AI 点餐体验。首页采用首页 B 的视觉主体与搜索入口 A 的搜索框交互；底部导航统一为首页、商家、订单、我的；AI 以用户可理解的“AI 助手”形式出现在相关点餐页面。

重构保留 XML + MVVM、OkHttp、Glide、现有 API 语义和业务闭环。页面统一实现加载、内容、空状态、错误、提交中和成功等状态；临时输入、购物车、地址选择、AI 会话和待支付订单支持旋转屏幕与进程重建后的恢复。

完整 Android 用户流程是最高测试 seam：

```text
登录或跳过登录
→ 首页
→ 搜索
→ 商家菜单
→ 选择规格
→ 单商家购物车
→ 结算
→ 创建待支付订单
→ 模拟支付
→ 订单详情与配送状态
```

AI 助手作为第二条完整用户流程接入同一业务闭环：

```text
输入需求
→ 展示执行进度
→ 生成候选订单
→ 修改或确认
→ 创建待支付订单
→ 模拟支付
→ 查看配送状态
```

## User Stories

1. 作为访客，我希望跳过登录浏览首页，以便快速了解应用。
2. 作为访客，我希望搜索商家和菜品，以便在登录前判断是否有合适的餐品。
3. 作为访客，我希望浏览商家菜单和菜品详情，以便决定是否登录点餐。
4. 作为访客，我希望在加购或创建订单时被引导登录，以便保护我的购物车和订单数据。
5. 作为用户，我希望登录成功后回到刚才的操作，以便不必重新选择商家、菜品和规格。
6. 作为用户，我希望在首页首屏看到搜索入口，以便快速找到商家或菜品。
7. 作为用户，我希望使用自然语言搜索需求，以便不用记住精确的商家或菜品名称。
8. 作为用户，我希望首页看到 AI 点餐入口，以便把选择餐品的工作交给 AI 助手。
9. 作为用户，我希望使用“清淡午餐”“30 元以内”和“再来一单”等快捷建议，以便快速开始常见任务。
10. 作为用户，我希望没有地址时仍可搜索和获得 AI 推荐，以便先探索餐品。
11. 作为用户，我希望确认订单前被要求补充有效地址，以便餐品送到正确地点。
12. 作为用户，我希望自动下单在没有默认地址时被阻断，以便避免订单发送到错误地址。
13. 作为用户，我希望通过四项底部导航切换首页、商家、订单和我的，以便形成稳定的应用结构。
14. 作为用户，我希望切换 Tab 后保留原来的滚动位置、筛选条件和输入内容，以便继续之前的浏览。
15. 作为用户，我希望再次点击当前 Tab 回到该 Tab 根页面，以便快速回到起点。
16. 作为用户，我希望首页展示附近好店、评分、配送时间、距离和价格信息，以便快速比较商家。
17. 作为用户，我希望首页加载时看到骨架屏，以便知道内容正在加载而不是页面失效。
18. 作为用户，我希望首页加载失败时可以重试，以便在网络恢复后继续使用。
19. 作为用户，我希望搜索无结果、网络失败和需要登录时看到不同提示，以便知道下一步该怎么做。
20. 作为用户，我希望从搜索结果进入商家菜单，而不是直接跳过菜品和规格选择，以便明确订单内容。
21. 作为用户，我希望查看商家封面、评分、配送信息和菜单分类，以便判断是否适合点餐。
22. 作为用户，我希望看到菜品图片、描述、价格和加购入口，以便快速选择餐品。
23. 作为用户，我希望选择菜品规格、辣度和加料，以便得到符合偏好的订单。
24. 作为用户，我希望售罄菜品和不可用规格明确显示并不能被加入购物车，以便避免无效下单。
25. 作为用户，我希望购物车只包含一个商家的商品，以便费用和配送关系清晰。
26. 作为用户，我希望切换商家时被提示购物车将被清空，以便避免误删当前选择。
27. 作为用户，我希望购物车数量和金额在加购、减购后立即更新，以便掌握订单成本。
28. 作为用户，我希望结算前重新校验价格、库存和地址，以便看到真实可提交的订单。
29. 作为用户，我希望结算页清楚展示地址、配送费、优惠和总金额，以便做出支付决定。
30. 作为用户，我希望创建订单后进入待支付状态，以便在模拟支付前仍能检查订单。
31. 作为用户，我希望取消或返回模拟支付时回到结算页并保留订单内容，以便继续修改或支付。
32. 作为用户，我希望支付失败时看到具体原因，并可以重新支付原订单，以便不产生重复订单。
33. 作为用户，我希望支付成功后看到订单详情和配送时间线，以便了解订单进度。
34. 作为用户，我希望订单 Tab 按全部、待支付、配送中和已完成筛选，以便快速找到订单。
35. 作为用户，我希望已取消和支付失败订单仍能在全部订单中查看，以便追溯异常。
36. 作为用户，我希望从首页、搜索、商家和订单页面打开 AI 助手，以便在点餐过程中随时获得帮助。
37. 作为用户，我希望 AI 助手只使用易懂的用户语言，以便不需要理解 Agent、模型或工具调用等技术概念。
38. 作为用户，我希望 AI 助手展示正在理解需求、寻找好店、查看菜品和准备订单等进度，以便知道任务没有卡住。
39. 作为用户，我希望 AI 助手支持文字输入和录音后识别，以便选择最方便的表达方式。
40. 作为用户，我希望语音识别结果回填输入框并可编辑，以便修正识别错误后再发送。
41. 作为用户，我希望 AI 候选订单展示商家、菜品、规格、数量、地址、配送费、优惠和总金额，以便在确认前完整检查。
42. 作为用户，我希望点击“修改”后可以用自然语言修改订单，以便处理复杂需求。
43. 作为用户，我希望直接在候选订单卡片中修改数量、规格和地址，以便快速处理简单修改。
44. 作为用户，我希望 AI 确认后创建待支付订单并进入模拟支付，而不是绕过支付步骤，以便流程符合普通点餐逻辑。
45. 作为用户，我希望 AI 创建订单前重新校验地址、价格、库存和金额上限，以便防止候选订单过期。
46. 作为用户，我希望 AI 会话在面板关闭或切换页面后保留，以便重新打开时继续对话。
47. 作为用户，我希望全屏 AI 面板返回时先收起为半屏，再关闭面板，以便返回行为可预期。
48. 作为用户，我希望设置页只展示面向用户的 AI 助手说明，不看到 API Key 或模型配置，以便降低理解和安全风险。
49. 作为用户，我希望在地址管理中新增、编辑、删除和设置默认地址，以便维护收货信息。
50. 作为用户，我希望默认地址不能被直接删除，以便始终保留有效的自动下单地址。
51. 作为用户，我希望结算页选择地址只影响当前订单，以便不会意外修改长期默认地址。
52. 作为用户，我希望长期自动下单必须配置默认地址和金额上限，以便控制自动化风险。
53. 作为用户，我希望金额超限、菜品下架、价格变化或授权过期时自动下单被阻断，以便保留最终控制权。
54. 作为用户，我希望旋转屏幕后继续看到当前页面内容，以便不中断点餐过程。
55. 作为用户，我希望进程被系统回收后能够恢复登录输入、搜索关键词、购物车、地址、AI 会话和待支付订单，以便尽量避免丢失进度。
56. 作为用户，我希望已支付订单从服务端重新加载，以便看到真实订单状态。
57. 作为用户，我希望无法恢复 AI 会话时看到会话过期提示和重新开始入口，以便明确恢复失败原因。
58. 作为用户，我希望页面中的按钮、图标、输入框和订单状态能被 TalkBack 正确读出，以便无障碍使用。
59. 作为用户，我希望应用在 360dp、393dp 和 412dp 宽度下不出现文字截断、按钮遮挡或底部栏覆盖，以便在不同手机上正常使用。
60. 作为维护者，我希望完整用户流程有 ViewModel 测试和 Maestro 流程测试，以便同时获得快速反馈和真实模拟器验收证据。

## Implementation Decisions

- 当前 UI、交互、页面状态、导航和 UI 验收标准以 `ui-redesign.md` 为唯一来源。
- Android 保持 XML + MVVM、单 Activity、多 Fragment、OkHttp、Glide、Coroutines/Flow 的技术方向；本规格不改变后端接口语义。
- 底部导航固定为：首页、商家、订单、我的。登录、注册、地址编辑和模拟支付页面隐藏底部导航或 AI 入口，具体可见范围遵循当前 UI 设计稿。
- 访客可以浏览首页、搜索、商家和菜品；加购、地址管理、创建订单和自动化策略要求登录。登录成功后恢复原操作。
- 首页使用首页 B 的视觉主体与搜索入口 A 的搜索框交互；首页不放独立历史订单卡片，“再来一单”是 AI 快捷建议。
- 首版购物车只允许单商家；切换商家时先提示用户清空购物车或取消。
- 普通和 AI 点餐的订单边界统一为：确认候选订单 → 创建待支付订单 → 模拟支付 → 查看配送状态。支付重试复用原订单。
- 没有地址时允许 AI 推荐和搜索；创建订单前必须有有效地址；自动下单必须有有效默认地址。
- AI 面板支持半屏和全屏；关闭或跨页面切换时保留会话、事件和候选订单。用户可见文案使用“AI 助手”和自然语言，不暴露技术架构名词。
- 设置页不提供 API Base URL、模型名称或 API Key 编辑入口；模型和服务端密钥属于服务端配置。
- 页面状态统一覆盖 Initial、Loading、Content、Empty、Error、Submitting、Disabled、AwaitingConfirmation 和 Success；AI 额外覆盖 Recording、Recognizing、Sending、Executing、CreatingOrder 和 OrderCreated。
- 返回键优先处理 AI 面板、规格弹层和当前页面栈；支付取消回到结算页，支付成功进入订单详情。
- 临时输入、搜索关键词、购物车、地址选择、AI 会话和待支付订单支持旋转屏幕及进程重建恢复；已支付订单以后端为事实来源。
- 订单状态向用户显示中文状态，不展示后端枚举名或异常堆栈。
- 控件必须提供稳定的 Resource ID 或 content description；布局避让和字号放大属于首轮验收范围。

## Testing Decisions

- 最高测试 seam 是完整 Android 用户流程，验证用户从进入应用到查看配送状态的外部行为，不测试 XML 层级或 ViewModel 私有实现细节。
- ViewModel 测试用于快速验证页面状态转移、访客登录恢复、购物车、地址、AI 会话、支付失败重试和进程恢复。
- Repository 测试继续使用 MockWebServer 或 Fake API，覆盖成功、空数据、网络失败、鉴权失败、价格变化、库存变化和重复请求。
- Android UI 测试验证 XML 页面上的可见状态、导航、返回键、弹层、键盘避让、按钮禁用和稳定控件标识。
- Maestro 流程测试运行在 Android 模拟器或设备上，覆盖普通点餐闭环、访客登录恢复、AI 确认闭环、支付失败重试和关键错误状态。
- Maestro 测试通过可访问文本、Resource ID、content description 和关系选择器定位控件；不依赖坐标作为默认选择方式。
- 控件树检查以 Maestro 实际可见的 Android Accessibility 层为边界，另行验证 TalkBack、图片按钮描述、输入框提示和底部固定控件避让。
- 测试优先验证用户可观察行为；视觉像素、内部 Fragment 实现和具体 Adapter 结构不作为主要断言。
- 现有 `FakeApiOrderingFlowTest`、`OrderingViewModelTest`、`OrderingRepositoryTest`、`AgentViewModelTest` 和 `SessionRouteCoordinatorTest` 作为测试先例，重构时扩展而不是重复建立同类业务测试。
- 每个实现切片至少提供一条快速测试和一条可在模拟器运行的 Maestro 验收流程；完整 UI 重构完成后再运行全套 Android 单元测试、UI 测试和构建验证。

## Out of Scope

- 不改造后端领域模型、API 语义、SSE 协议或 Agent 工具授权规则。
- 不接入真实外卖平台、商家端、骑手端、地图定位或真实支付。
- 不把 Android 改为 Jetpack Compose；本次保持 XML。
- 不在 Android 端运行 LLM、LangGraph 或保存服务端 API Key。
- 不实现多商家购物车。
- 不实现实时语音转写、语音播报或边说边显示识别结果。
- 不把“Agent”技术概念作为用户产品文案的一部分；内部代码、接口和测试可以继续使用既有技术名称。
- 不在本规格中决定深色模式的完整视觉方案；仅保留为后续打磨项。
- 不重写历史 spec、历史 plan、任务报告或验证报告的历史事实。

## Further Notes

- 现有 HTML 原型是历史/实验产物，不参与 Android UI 的视觉还原和验收；Android 实现直接依据 `ui-redesign.md` 及其引用的设计稿。若原型与设计稿冲突，忽略原型。
- 新实施计划应从 Android UI 重构开始，不沿用旧的全栈初始化顺序。
- 当前执行任务已重新发布到 `.scratch/ui-redesign/issues/`，共 8 个按视觉重建范围与 blocking edges 划分的 Android Tickets；`.scratch/ui-redesign-v2/issues/` 为已废弃的过渡草案。所有 Android UI Ticket 都必须以 `ui-redesign.md` 的确认图片为唯一视觉基准。
- 文档讨论记录 Q1–Q30 已保存于 `.scratch/ui-redesign/grilling/round-01.md`；达到 Q60 后继续保存下一轮记录。
