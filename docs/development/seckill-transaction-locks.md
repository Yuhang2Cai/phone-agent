# 秒杀交易锁序与持久化边界

本文件记录实现决策，不能修改已确认r1+r3规格或降低验收条件。当前开发中，尚未取得真实并发、恢复及完整交付证据。

## 写入入口

已有任务写入先经过任务/确认栅栏；页面在任何领域行锁前通过`requireDomainEntry`拒绝任务专属凭证。任务与页面不能交叉消费同一确认凭证。

|路径|锁顺序|事务内事实|
|---|---|---|
|报价创建|普通读取活动、套餐和数据库时间；不占库存|报价快照、确认凭证|
|页面/旧API/Agent统一建单|既有任务栅栏（适用时）→用户→报价→原请求回执→专属套餐→活动→确认消费→新订单→个人额度→新预留|原请求回执、确认消费、报价消费、订单/券、预留、额度和套餐库存同事务|
|支付|既有任务栅栏（适用时）→本人订单→确认消费（适用时）→专属套餐→预留→额度|预留转COMMITTED、额度类别转换、实付快照同事务|
|超时关闭|订单→专属套餐→预留→额度|预留转RELEASED、额度释放、套餐库存归还、订单关闭同事务|

新建订单/预留是当前事务的新增行，不等待另一笔既有订单；支付和释放不反向锁用户或报价，因此不会形成“创建持用户等套餐、释放持套餐等用户”的环。任何新增退款、维护或管理写者都必须重新核对该依赖图。真实MySQL竞态仍为必需证据，锁序分析不能替代实测。

MySQL可重复读验收暴露过旧快照问题，首次失败记录不可删除。所有资格依赖的已托管实体都使用带锁refresh取得当前事实；不能find加锁后又用普通refresh读回旧库存。回执通过唯一键原子占位取得已存在行，再按当前读恢复原订单；避免在不存在订单范围上加间隙锁导致其他用户插入等待，也避免事务早先的快照漏掉已经成功的订单。幂等重放只读取既有订单，不再锁套餐或消耗新授权。

## 时间与库存

创建取得套餐及活动锁后读取数据库UTC时间；支付取得订单、套餐、预留及额度锁后重新读取，不使用排队前的时间。订单创建时间由该瞬时转换为现有上海业务LocalDateTime，公开时仍转UTC；独立`payment_expires_at`为同一瞬时加300秒，券截止保持原有效期。

套餐`inventory`是唯一剩余库存；个人额度保存RESERVED与COMMITTED计数；每订单唯一预留保存数量与结算状态。活动结束或停止只影响新购，不影响已创建订单在原期限内支付。退款不修改秒杀库存或额度。

## 已知待闭合项

扫描/本进程维护停写已实现，真实MySQL最后库存和同键旧快照复验通过；100轮支付竞争、恢复性能及维护/备份真实组合仍待验收。HTTP稳定错误信封、个人资格与原请求查询、全部券可用性投影、全入口组合及Android尚未闭合。不得将定向测试通过解释为全部秒杀交易可交付。
