# AG07 双库与索引备份恢复

此流程只用于已登记自有目标。AG07-06提供有界文件/水位/导入编排和固定MySQL命令；Docker/数据库/Chroma事实由AG07-07受信适配器现场取证。没有真实恢复证据前不宣称灾备能力，也不承诺RPO=0、RTO或并发容量。

## 备份范围与限制

来源必须是不同完整ID的Agent库、Spring库、Chroma，匹配AG07创建台账及实际owner、镜像、专属卷和回环端口。不得从当前inspect反填期望，不采用旧脚本默认mysql-server/3306。

每份文件上限256MiB，三份合计至多768MiB；索引最多10000普通文件/目录，解包后同样256MiB；单表最多100000行且编码字节最多256MiB，表数最多256。备份和恢复各有120秒截止；实际外部命令必须沿同一剩余截止执行，不能仅在回调返回后检查。超限保留失败现场并标受阻，不截断、不删表、不另开一轮。无空闲内存门槛，实际OOM仍是失败。

输出必须新建于已核私有ACL的绝对目录，拒绝链接、已有输出、归档路径穿越和特殊文件。SQL、索引和业务摘要都可能敏感，不进入Git或公开日志；秘密从容器已有私有环境获取，不出现在argv。异机存储未具备独立加密配置时不上传。

## 停写一致备份

由发布模块正常关闭新普通入口、排空并停止全部写者，取得同后端一次维护凭证。清单、产物/目标观察、凭证时限、普通/控制/同步工作/未知写/后台写者计数在备份过程中保持有效；缺字段或未知值拒绝。

适配器先取两库全部表及InnoDB引擎清单、完整Flyway历史、权威task/run/turn/epoch/原执行键闭合摘要、确认状态与持久恢复预算，以及索引内容/集合摘要。逐表摘要沿历史 `verify_retirement_backup.py` 的规范JSON排序算法，但改为有界消费；原脚本不修改。

两库分别使用固定mysqldump命令，包含routines/events/triggers，禁止--databases及数据库重定向。索引在停写后归档专属卷，不调用embedding、不自动重建。两库及索引全部完成后重读源身份、全部摘要和停写计数；一致才写manifest.json。清单记录文件大小/SHA、源码配对、配置/契约SHA、维护计划SHA和完整事实。单库single-transaction不能替代该双来源停写证明。

## 新目标恢复

先验证整套清单摘要、每个文件及索引成员，然后检查三个新目标。目标容器必须由本任务显式创建台账登记；目标库/索引为空且未有业务，不能是任一源ID，不能复用源库名或共享卷。`exists=false`指目标库/索引未初始化，不表示可凭空捏造Docker ID。克隆库使用ag07_restore_前缀及独立凭据。

同一个恢复轮次按Agent库、Spring库、Chroma依次导入；不在此步骤启动应用或开放入口。核恢复的完整表/迁移/业务键/确认/预算/索引摘要与备份一致，源前后摘要仍一致。失败保持入口关闭，保留源和有效备份。删除只允许显式台账中本轮新建且再次核ID/owner的空闲目标；不自动删除失败证据或旧有效恢复点，不使用模糊容器名或全局prune。

真实服务目录、原receipt、旧确认拒绝、恢复不自动执行、已提交动作不重写等仍需在07用恢复后的真实服务核查；文件摘要一致不替代业务行为验证。运行日结束前及每次发布前备份；最近成功点超过24小时提示，尚未配置生产调度前不声称自动备份已启用。
