# 饭搭子 AI：Android 外卖点餐 Agent 设计

## 1. 项目定位

“饭搭子 AI”是一个面向个人作品集和 Android 技术面试的外卖点餐项目。项目同时强调两条主线：一套完整、可安装的 Android 用户端，以及一个能够通过受约束工具完成真实点餐闭环的 AI Agent。

项目不接入真实外卖平台、商家端、骑手端或真实支付。商家、菜品、地址、订单和用户数据由本项目后端维护；支付后的配送状态由后端定时状态机模拟。

## 2. 目标与非目标

### 2.1 目标

- 提供注册、登录、浏览、搜索、选规格、加购、下单、模拟支付和订单追踪的完整用户流程。
- 提供全局悬浮 AI 助手，支持文字及本地离线语音输入。
- Agent 可以搜索全平台商家和菜品、读取偏好及历史订单、构建候选购物车并在授权边界内创建订单。
- 默认在下单前展示订单确认卡片；支持本次全自动授权和带约束的长期自动模式。
- 通过可观察的工具调用事件、自动化测试和场景评测展示 Agent 的可靠性。
- 先交付一套可编辑的 HTML/CSS 交互原型，再依据原型实现 Android XML 页面。

### 2.2 非目标

- 不开发商家端、骑手端和运营后台。
- 不接入支付宝、微信或真实资金链路。
- 不接地图定位、地图选点或真实配送轨迹。
- 不做跨平台真实外卖比价或第三方 App 自动化。
- 首版不使用多 Agent，不提供疾病诊断、治疗或用药建议。
- 首版 ASR 不提供边说边显示的实时转写。

## 3. 技术架构

### 3.1 Android 客户端

- Kotlin
- XML 布局
- 单 Activity、多 Fragment
- MVVM 分层
- OkHttp 直接访问后端 API，统一封装请求、鉴权、超时、重试和错误映射
- Glide 加载商家、菜品和用户头像图片，配置内存及磁盘缓存
- Room 保存必要缓存和草稿状态
- Kotlin Coroutines 与 Flow 管理异步状态
- 本地 Sherpa-ONNX Paraformer 模型完成中文离线 ASR

建议模块边界：

- `presentation`：Activity、Fragment、Adapter、BottomSheet、ViewModel
- `domain`：UseCase、领域模型和 Repository 接口
- `data`：OkHttp API 客户端、Room、Glide 图片加载、DTO、Repository 实现
- `core`：鉴权、网络、错误映射、日志、设计规范
- `asr`：录音、音频解码和本地识别
- `agent-ui`：悬浮球、聊天面板、执行事件和确认卡片

### 3.2 Spring Boot 后端

- Java 17
- Spring Boot
- Spring Security + JWT
- Spring Data JPA
- MySQL
- OpenAPI/Knife4j 接口文档
- SSE 推送 Agent 执行事件，因为当前交互以服务端单向流式事件为主
- 大模型 API Key、Base URL 和模型名称仅通过服务端环境配置提供

后端保持一个可部署单体，业务模块和 Agent 模块在代码边界上隔离，但共享用户身份、数据库事务、校验规则和可观测能力。首版不单独部署 Python Agent 服务。

### 3.3 总体数据流

```text
文字输入或本地 ASR
  -> Android 提交用户指令
  -> Spring Boot AgentOrchestrator 调用大模型
  -> 大模型选择白名单工具
  -> 后端校验身份、参数、业务状态和授权
  -> 后端执行工具并记录事件
  -> SSE 向 Android 推送可读执行摘要
  -> Android 同步更新页面和候选购物车
  -> 用户确认，或后端验证自动化授权
  -> 创建订单并进入模拟支付与配送流程
```

Android 不直接连接大模型。价格、库存、地址、权限和订单状态均以后端及数据库为最终事实来源。

## 4. Android 页面与导航

底部导航包含：首页、订单、我的。

页面范围：

1. 启动页、注册页、登录页
2. 首页：当前地址、搜索、分类、推荐商家、AI 浮球
3. 搜索结果：商家和菜品结果
4. 商家详情：菜单分类、菜品列表、规格选择、店内购物车
5. 确认订单：地址、订单项、备注、配送费和最终金额
6. 模拟支付：确认支付、取消支付
7. 订单详情：支付及配送状态时间线
8. 订单列表：进行中、历史订单和再次购买
9. 地址管理：新增、编辑、删除和设置默认地址
10. 个人中心：账户信息、口味偏好和自动化设置
11. AI 助手：半屏聊天、全屏聊天、执行轨迹和订单确认卡片

AI 浮球显示在首页、搜索、商家和订单页面；登录、注册和模拟支付期间隐藏。

## 5. UI 与可编辑原型

### 5.1 品牌与视觉

- 品牌名称：饭搭子 AI
- 参考成熟外卖产品的信息架构和交互习惯，不复制第三方 Logo、品牌文字和原始素材
- 主色采用明亮黄色
- 背景采用浅灰白，内容使用白色卡片
- AI 功能使用少量蓝紫渐变和状态光效
- 使用统一线性图标、系统无衬线字体和中等圆角
- 原型基准视口为 390 x 844

### 5.2 HTML/CSS 原型

原型由可直接编辑的 HTML、CSS、JavaScript 和本地素材组成，不连接真实后端。CSS 变量统一管理颜色、字号、间距、圆角和阴影。

原型至少覆盖：

- 登录与注册
- 首页与搜索
- 商家详情、规格选择和购物车
- 订单确认与模拟支付
- 订单配送状态
- 地址及自动化设置
- AI 半屏、全屏和执行状态
- 文字输入与模拟“录音后识别”效果
- 普通确认下单与本次自动下单

### 5.3 AI 助手交互

- 全局右下角展示悬浮球。
- 点击后打开半屏 Bottom Sheet，不打断当前页面。
- 面板可上拉进入全屏聊天。
- Agent 搜索、推荐和加购时，底层页面同步更新并高亮结果。
- 浮球和面板展示思考中、执行中、待确认、已完成和失败状态。
- 仅展示“正在搜索商家”等可读执行摘要，不展示模型隐含推理过程。

## 6. 本地语音识别

复用 `redBook` Android 项目的 Sherpa-ONNX 方案：

- Sherpa-ONNX 1.12.39
- 中文 Paraformer small 2024-03-09 INT8 模型
- 16 kHz 单声道输入
- CPU 推理，默认 2 个线程
- 模型随 APK 打包，不在运行时下载

交互流程：按住录音，松开结束，本地识别，文本回填，用户可以编辑后发送。识别失败时保留当前输入状态并允许重试，不发送空消息。

模型约 78 MB，运行库约 54 MB。README 需说明项目用安装包体积换取离线可用、隐私和低网络依赖。

## 7. 数据模型

- `User`：账号、密码摘要、昵称和账户状态
- `Address`：收货人、手机号、详细地址、默认标记
- `Merchant`：名称、评分、起送价、配送费、预计送达时间和营业状态
- `Dish`：商家、分类、名称、描述、价格、图片和上下架状态
- `DishOption`：规格组、规格项及价格增量
- `CartDraft`：用户当前候选购物车和来源
- `CartDraftItem`：菜品、数量、规格及计算价格
- `Order`：用户、地址快照、金额、支付状态、配送状态和幂等键
- `OrderItem`：菜品、规格和下单时价格快照
- `UserPreference`：忌口、过敏、口味、常用预算和确认状态
- `AutomationPolicy`：长期自动开关、默认地址和最高金额
- `AutomationGrant`：本次任务的短期自动化授权、范围和失效时间
- `AgentSession`：用户会话和当前任务状态
- `AgentEvent`：工具名称、执行阶段、摘要、结果状态和时间

商家与菜品通过初始化脚本导入，目标数据量为约 10 家商户、80 至 120 个菜品。订单和订单项保存快照，避免菜单变化破坏历史订单展示。

## 8. 订单、支付与配送状态

```text
待支付
  -> 已支付
  -> 商家已接单
  -> 制作中
  -> 骑手已取餐
  -> 配送中
  -> 已送达
```

- 后端真实创建订单并生成唯一订单号。
- 模拟支付页支持确认和取消。
- 创建订单和支付操作使用幂等键，重复点击不得创建重复订单或重复支付。
- 支付后的配送状态由后端定时状态机推进。
- Android 始终读取后端状态，应用重启后状态保持一致。

## 9. 单 Agent 设计

首版仅提供一个 `FoodOrderingAgent`。Agent 负责理解、澄清、规划工具顺序和解释结果；确定性业务工具负责查询和修改真实状态。

白名单工具：

- `search_merchants`
- `search_dishes`
- `get_dish_detail`
- `get_user_preferences`
- `get_default_address`
- `get_last_order`
- `create_cart_draft`
- `update_cart_draft`
- `validate_cart`
- `create_order`
- `get_order_status`

工具输入使用结构化参数和服务端校验。模型不能直接访问数据库、HTTP 业务接口或支付逻辑。

### 9.1 标准流程

```text
理解需求
  -> 必要时澄清
  -> 搜索并推荐
  -> 构建候选购物车
  -> 后端校验
  -> 展示确认卡片
  -> 获得授权
  -> 创建订单
  -> 模拟支付
```

### 9.2 历史订单复购

“按上次配置点单”读取最近一笔已支付订单，锁定原商家、菜品、数量和规格：

- 菜品或规格下架时终止复购并提醒，不跨店替换。
- 使用当前价格重新校验和计算金额。
- 确认模式下必须再次确认。
- 自动模式下只有地址有效且金额不超过授权上限时才能继续。

### 9.3 健康情境

单 Agent 可以处理“我感冒了，中午推荐吃什么”等需求，但仅将其作为饮食筛选情境：

- 不诊断疾病，不声称食物可以治疗疾病。
- 不提供药物建议或替代医疗意见。
- 结合用户过敏、忌口和在售菜品提供一般性推荐。
- `HealthSafetyPolicy` 作为确定性规则组件运行，不作为第二个 Agent。
- 出现严重或持续症状描述时停止自动推荐，并提示用户寻求专业医疗帮助。

## 10. 授权与安全边界

### 10.1 默认确认模式

创建订单前展示确认卡片，包含商家、菜品、数量、规格、地址、配送费和总金额。用户明确确认后才能调用 `create_order`。

### 10.2 本次自动模式

授权仅对当前 Agent 任务有效，并绑定用户、会话、地址、金额上限和失效时间。任务完成、取消、超时或会话结束后授权立即失效。

在授权范围内，本次自动模式允许 Agent 创建订单并自动完成模拟支付；真实支付始终不在项目范围内。

### 10.3 长期自动模式

用户必须在设置页主动开启，并配置默认地址和金额上限。发生以下情况时强制确认：

- 无有效默认地址
- 金额超过上限
- 菜品或规格不可用
- 价格发生影响授权范围的变化
- 后端判断工具请求与用户目标不一致

授权判断必须由后端执行，模型和 Android 客户端均不能绕过。

在长期策略有效且本次订单通过全部校验时，Agent 可以创建订单并自动完成模拟支付。

## 11. 错误处理与恢复

- 网络失败：保留输入、会话和候选购物车，允许重试。
- 模型超时：结束当前执行步骤并允许重新发起，不重复执行已成功的写操作。
- 工具参数错误：后端拒绝并返回可修正的结构化错误。
- 库存或价格变化：重新校验并更新确认卡片。
- 菜品下架：复购流程终止，普通推荐流程允许重新搜索。
- 地址失效：暂停自动化并要求用户选择地址。
- 重复调用：使用请求 ID、工具调用 ID 和订单幂等键去重。
- ASR 失败：允许重录或改用文字输入。

## 12. 测试策略

### 12.1 Android

- ViewModel 状态流转单元测试
- Repository 的网络、缓存和错误分支测试
- OkHttp API 客户端使用 MockWebServer 覆盖成功、超时、错误码和鉴权失败场景
- 登录、搜索、加购、地址、确认和订单流程测试
- ASR 初始化失败、空结果和权限拒绝测试
- 屏幕旋转、进程重建和网络恢复测试
- 关键用户流程的 UI 自动化测试
- Glide 图片加载的占位图、错误图和缓存命中场景测试

### 12.2 后端

- 注册登录、JWT 和资源归属测试
- 搜索与筛选测试
- 购物车价格、规格、库存和地址校验测试
- 订单创建及支付幂等性测试
- 自动化授权范围测试
- 配送状态机测试
- 非白名单和未授权工具调用拒绝测试

### 12.3 Agent 场景评测

使用可重复场景记录工具序列、参数、确认行为和最终订单结果：

- 30 元以内的辣味午餐
- 按上次配置复购
- 感冒时推荐清淡午餐
- 不要香菜并使用默认地址
- 菜品下架、价格变化、地址缺失和金额超限
- 模型超时、非法参数和重复工具调用

自动化测试使用模型响应桩验证确定性业务规则；另设少量在线评测验证真实模型行为，避免测试套件完全依赖外部模型稳定性。

## 14. 实施顺序约束

1. 先完成并验收 HTML/CSS 可编辑原型。
2. 再建立后端领域模型、认证、菜单、地址和订单基础能力。
3. 实现 Android 标准外卖流程。
4. 接入本地 ASR。
5. 实现 Agent 工具、编排、授权和流式事件。
6. 完成自动化测试、在线场景评测和作品集材料。

首个实现计划必须继续拆分为可独立验证的阶段，避免同时开发全部页面、后端和 Agent。
