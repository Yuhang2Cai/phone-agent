# 活动与金币事务边界

`ActivityRules` 计算上海自然日的权威进度，`ActivityStore` 批量读取本人订单/券/退款事实，`ActivityService` 组合唯一实例、幂等请求、奖励凭据、流水及账户余额。`ActivityClock` 生产使用系统时钟，HTTP 不接受客户端时间、完成次数或奖励金额。

每日任务按用户/定义/业务日期唯一；连续任务按用户/定义/活动周期唯一。领取保存规则快照，配置新版本不能改写旧实例。列表保留近七天结束记录和当前连续周期的原实例，更早记录仍可凭原实例或原请求键回读。公开定义不会在迁移中插入示例运营任务。

## 写入和锁顺序

同用户活动写入先建立并锁定 `coin_accounts` 行，再按需要锁任务实例、订单、券、退款、奖励凭据和流水。退款申请在获取券行锁之前也锁定相同账户行。确认凭证入口检查只读不可变绑定，真正消费在领域资格核查后执行，不反向等待活动账户。

MySQL 默认 REPEATABLE READ 下，等待账户锁后必须使用当前读重新读取实例、支付和退款事实；写路径回执也使用当前读，避免事务此前建立的快照看不到其他请求刚提交的奖励。纯读取接口保持同一只读事务快照。

发奖同一事务写凭据、完整订单依据、唯一奖励流水、余额、实例状态及幂等键。任何阶段失败整体回滚；不同任务共享同一有效订单，但同一实例最多一份奖励。客户端超时不能证明未提交，必须按原请求或原实例只读核查。

`coordinateRefundCompletion` 是没有公共 HTTP 路由的可信内部适配点。调用方的终态更新必须加入当前事务；若用 JPA 修改实体，须在回调返回前显式 flush，确保 JDBC 重新核查时能看到该变更。回调失败或重算失败共同回滚。申请/批准只冻结未发奖励；真正成功退款才可使既有奖励失效并产生唯一冲正。窗口内还有足够其他订单时保留奖励。真实退款执行仍延期。

## 验证入口

- `ActivityRulesTest`：支付时刻、本人归属、多份一单、自然日及连续窗口。
- `ActivityLedgerMysqlTest`：独立 MySQL 合成库、真实迁移、20并发唯一发奖、回滚、退款终态、跨日原请求恢复。
- `ActivityInputTest` / `ActivityAdmissionTest`：严格输入和有界准入。
- `scripts/Verify-ActivityHttp.py`：固定本机8160，通过真实认证、报价、订单、模拟支付、活动及退款服务验证组合；输出目录必须位于 `.runtime`，不得提交其中凭据。

实际验收结果、源码身份和必需项状态在 Agent 仓库的活动验收报告中记录；测试代码存在不表示已经运行通过。
